# Claude Code エージェントでの開発ワークフロー

Claude Code のエージェントが実装し、人間が実機で確認する体制で Godot C# プロジェクトを進めるときの運用ルール。

## CLAUDE.md の分け方

| ファイル | 書くこと |
|---|---|
| ルートの `CLAUDE.md` | 応答言語、リポジトリの構成、git の運用、委譲の方針、ファイル編集のルール、コマンド、検証の分担、作業範囲 |
| `godot/CLAUDE.md` | プロジェクトの構成、環境（Godot のパス・SDK・export templates・署名）、コマンド、C# の規約（**理由と発見の経緯を添える**）、テストの規律 |
| `.claude/skills/<name>/SKILL.md` | 必要なときだけ使う手順（例: 自動操作・スクリーンショット）。CLAUDE.md から外し、常に読み込まれないようにする |

- 規約は「〜しない」だけでなく、**なぜ駄目か・何が起きたか**を書く。理由が無いと、エージェントは同じ失敗を「改善」として繰り返す
- CLAUDE.md が肥大化したら、経緯の部分を `docs/` のアーカイブに移す。CLAUDE.md には現在のルールだけを残す

雛形: [templates/CLAUDE.md.template](../templates/CLAUDE.md.template)

## 委譲の構成

```
main（計画・設計判断・検証） ──brief──▶ coder（仕様が明確な実装）
                                  ├──▶ explorer（所在の特定・読み取り専用）
                                  └──▶ advisor（行き詰まり・全体設計の相談）
```

- **main はソースコードを編集しない。** docs、memory、CLAUDE.md の編集は main で行ってよい
- brief には **目的・関係するファイル・決定済みの設計・完了条件**（例: `dotnet build` と `dotnet test` が通る）を書く
- coder から戻った成果物は main が必ず検証する（差分の確認と build + test）
- 同じ問題で修正→検証が 2 回失敗した、仮説が尽きた、アーキテクチャ全体に関わる、のいずれかなら advisor に問題・試したこと・失敗内容・関連パスを渡して相談し、返ってきた方針で coder に委譲する
- **brief では `git checkout` / `git restore` / `git stash` / `git clean` を禁止する。** 作業ツリーは共有されていて、サブエージェントには、見慣れない変更が誰のものか区別できない。実例では main が編集中だった docs を消された。範囲外の変更を見つけたら、触らずに報告させる
- 実装をプランモードの承認フローに乗せない。承認後のサブエージェント起動を、権限の分類器が「根拠のない承認」と判断して拒否する。大まかな設計を会話で固めてから委譲する
- コードレビューは main が行う（所在の確認だけ explorer に任せる）。`/code-review` や `/simplify` などフォークで実行されるスキルは親のモデルを引き継ぎコストが高いので、ユーザーが名指しで頼んだときだけ、確認を取ってから使う

### サブエージェントの癖と対処

| 症状 | 対処 |
|---|---|
| 完了通知の result が報告の形になっていない（途中の一文で切れている） | 完了扱いにせず、SendMessage で最終報告を求める |
| ターン数の上限に達し、報告なしで止まる | SendMessage で「追加の調査はせず、今ある分だけ報告して」と指示する |
| 数十箇所に及ぶ機械的な修正で、上限に達し続ける | brief の時点でファイル単位に分割し、複数の coder に分けて出す |
| coder が未完了のまま報告してきた | 途中までの成果は作業ツリーに残っている。main で `git status` と build + test を実行し、残りを切り出して再委譲する |
| 委譲先のエージェント名が見つからない | プラグインの接頭辞を付けたフルネーム（`model-routing:coder` など）で指定する |

## 検証の分担

- **エージェントの完了条件は build + test まで。** `dotnet build` と `dotnet test` が通ればよい
- Godot 側の変更を終えるときは、
  1. `godot/tools/run.sh` で debug ビルドを起動し、**ウィンドウを開いたままにする**（サブエージェントが起動したウィンドウはすぐ消えるので、起動は main から行う）
  2. 「何を変えたか・どこを見ればよいか・どう動けば正しいか」のチェックリストを渡してターンを終える
- iOS の場合は、実機へのインストールまでを行う（[native-ios.md](native-ios.md)）
- スクリーンショットや合成入力（osascript など）による自動操作は、人間がその会話で**明示的に頼んだときだけ**使う。不安定で、トークンも多く消費する
  - 頼まれた場合の手順は、このプラグインの `godot-agent-driving` skill にまとめてある（ウィンドウ単位のスクリーンショット、合成入力の癖）

## サンドボックスでのコマンド

[build-test-tooling.md](build-test-tooling.md) の「サンドボックスでの注意」を brief にそのまま書く。

- `dotnet build ... -m:1 -nodeReuse:false --disable-build-servers`
- `dotnet test ... -m:1 -nodeReuse:false --disable-build-servers --no-build`（サンドボックスを外す）
- `godot ...`（サンドボックスを外す）
- サンドボックスを外すコマンドは単独で実行し、`&&` などで他のコマンドと連結しない
- サードパーティのアドオンや NuGet パッケージの追加は、ユーザーに確認する
- ファイルシステム全体を走査する検索（`find /` など）はしない。リポジトリの中だけを探す

## ファイル編集のルール

- **ソースは Edit / Write ツールでだけ編集する。** `sed -i`、`perl -pi`、ファイルを書き換える `python` / `node` のワンライナーは使わない
  - スクリプトで書き換えると、人間がレビューできる差分になる前に変更が入ってしまう。また「編集の前に読む」というチェックを迂回する
  - 修正が大きすぎて Edit では無理だと感じたら、スクリプトに頼る前に範囲を相談する
- **生成物は手で編集しない。** 生成元を直して再生成する（`godot/assets/`、テストベクターなど）
- 削除の経緯をソースのコメントに書かない（「〜は撤去した」など）。経緯は docs の履歴に書く
- コメントは最小限にする。ただし「なぜこうなっているか」がエンジンの癖に由来する箇所には、発見の経緯を添える

## docs の運用

```
docs/
  README.md          … インデックス。文書ごとに 1 行
  <GAME>_SPEC.md     … ゲームのルール仕様（エンジン非依存。これが正）
  RELEASE_TASKS.md   … 配布前の準備だけ（通し確認・アイコン・配布形態）
  features/*.md      … 機能ごとに 1 ファイル
  ROADMAP.md         … 配布後の候補・スコープ判断が必要なもの
  PROGRESS.md        … セッションごとの履歴（追記のみ）
```

- 1 つのタスクは、`RELEASE_TASKS.md`・`features/*.md`・`ROADMAP.md` の**どれか 1 箇所にだけ**書く
- 実装の経緯や調査の記録は `PROGRESS.md` に追記し、タスク文書からはエントリ名で参照する
- 機能が完了しても `features/` のファイルは消さない。状態を「完了」にし、調整用のパラメータや既知の癖を残す
- 機能ファイルの構成は [templates/feature.md](../templates/feature.md) を参照（状態 / 決定事項 / 残タスク / 保留・見送り / 完了履歴 / 関連）
- 終わった大きな作業のログ（例: エンジン移行）は凍結する。ソースのコメントから参照されているなら、場所も動かさない

## memory に残すもの

コードや git の履歴からは分からない、環境・運用上の事実だけを残す。

- 環境の癖（Godot の起動方法、サンドボックスでのコマンドの通し方、端末の ID）
- 人間から受けた運用上の指示（検証の分担、委譲の方針）と、その理由
- サブエージェントの癖とその対処
